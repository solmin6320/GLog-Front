# A2. 도메인 규칙 분석 — 프론트가 표시하고 지켜야 하는 업무 규칙

> 작성 2026-10-02 · 담당: 도메인 규칙 분석
> 근거 문서와 약칭 — **「기능」** 기능명세서 v1.9 · **「화면」** 화면설계서 v0.7 · **「DB」** DB명세서 v0.4 · **「목업」** 목업 v2 (웹 W-01~W-16, 앱 A-01~A-08) · **「인계」** `_인수인계.md`
> 표기 — **(확정)** 명세에 명문 규정이 있다 / **(제안)** 명세에 근거가 없고 이 문서가 처음 내놓는다 / **(추측)** 명세 취지에서 도출했다. 화면설계서가 이미 (제안)·(추측)을 단 항목은 **「화면 제안」**처럼 출처와 함께 옮긴다.
> 범위 — 웹 프론트(React). 앱(RN)·백엔드 내부 로직은 다루지 않는다. 단, **목(mock) API가 지켜야 할 계약**은 다룬다. 실제 백엔드로 바꿔 끼울 때 화면 코드를 고치지 않으려면 목이 같은 규칙을 재현해야 하기 때문이다.

## 0. 한 장 요약

| # | 결론 | 근거 |
|---|---|---|
| 1 | **프론트는 판정하지 않는다.** 통과·미달·제외·면제·보류, 인증일 수, 경고 수, 연속 통과, 벌칙 대상, 팀별 경고, 기록글 인정은 전부 **서버가 계산한 값을 표시만** 한다. 프론트가 하는 계산은 "3 − n" 같은 **표시용 산술**뿐이다 (2-2절) | 기능 5·6장, DB 4-3, 화면 5-2-3 |
| 2 | **비공개 팀 이름은 서버가 가려서 내려준다.** 프론트가 받은 이름을 CSS로 숨기면 개발자 도구로 그대로 보인다. 목 API도 가린 값을 내려야 한다 (4절) | 화면 5-2-4, E-23 |
| 3 | **권한은 두 층이다.** 계정 상태·사이트 역할(전역)은 라우트 가드가, 팀장·팀원·작성자(자원 단위)는 자원을 조회한 뒤 서버가 내려준 관계 플래그로 판정한다. 비공개 팀 글은 팀 정보가 가려져 오므로 프론트가 "이 글 팀의 팀장인가"를 스스로 계산할 수 없다 (1-3 G-4) | 화면 5-2-1, 5-2-2, 5-1-8 |
| 4 | **로그인 완료·승인 확인 후 목적지는 항상 `/`다.** 원래 가려던 경로로 되돌리는 기능(returnTo)을 만들지 않는다 (확정) | 기능 10장 기본 화면, 화면 4-3 |
| 5 | **"오늘 오전 6시 기준"은 고정 문자열로 박지 않는다.** 갱신 시각 6시 자체가 「화면 제안」이고, 0~6시 사이와 갱신 실패 시에는 문구가 사실과 달라진다. 서버가 주는 기준 시각(asOf)으로 문구를 만든다 (제안 · 3-2절) | 화면 5-2-6 |
| 6 | **"이번 주"와 오늘 날짜는 서버 시각(KST) 기준이다.** 브라우저 시계·시간대를 판정성 판단에 쓰지 않는다. 배너 표시 같은 순수 표시에만 쓴다 | 기능 5장, 화면 E-27 |
| 7 | 경고 수를 세는 기준이 **화면마다 3가지**다 — TM-05는 그 팀 카테고리만, PR-01 팀별은 중복 집계, 나머지는 사람 단위 누적. TM-05에는 벌칙 대상 표시를 절대 넣지 않는다 (2-5절) | 기능 2·8장 |
| 8 | 문구는 **5-4장 최종 문구를 그대로 쓴다.** 다만 합쇼체가 섞인 8건, 같은 예외에 문구가 둘인 1건, 버튼이 다른 1건이 있어 정리가 필요하다 (6-4절, 10절) | 화면 5-2-8, 5-4 |
| 9 | 명세 간 충돌 **28건**, 의뢰인 확인 필요 **8건**을 10·11절에 모았다 | — |
| 10 | **면제는 사람 단위다.** 개인 면제가 승인되면 그 회원이 속한 모든 팀의 TM-05에서 "제외"로 보인다. 월요일 판정이 지난 주의 개인 면제를 승인하면 소급 면제이므로 미리보기를 거쳐야 하는데, 화면설계서는 [승인]을 즉시 처리로 적었다 (2-7, C-25) | 기능 7장, 화면 5-1-17, 5-1-10 ②-3 |

### 1-1. 상태 모델

### 2-5. 경고 수를 세는 기준 — 화면마다 다르다

| 화면 · 위치 | 세는 단위 | 금지 사항 | 근거 |
|---|---|---|---|
| **TM-05 ⑥ 경고 칸** | **그 팀 카테고리가 붙은 경고만** | 전체 누적 표시 금지, **벌칙 대상 배지 금지** — 다른 팀 경고 존재가 새어 나간다 | 기능 2장, 화면 5-1-5 하단 (확정) |

### 2-6. 화면 5-2-5 정책 대조 — 각 행이 화면에 미치는 영향

5-2-5는 "화면 표시에 직접 영향"이 있는 판정·경고 정책 14행이다. 행마다 **어느 화면의 무엇을 결정하는지**, 프론트가 그 정책으로 **무엇을 계산하면 안 되는지** 대조한다. 자세한 내용이 다른 절에 있으면 위치만 적는다.

| 5-2-5 항목 | 정책 요약 | 화면에 미치는 영향 | 프론트 책임 | 상세 |
|---|---|---|---|---|

| 인증일 | 잔디 1칸 이상 **또는** 기록글. 둘 다 있어도 1일 | 주간 스트립 · AC-01 ② 일자표에서 **기록글만 있는 날도 인증일**이다. 잔디 · 기록글 · 인증일을 따로 그린다 | 날짜별 `verified`를 서버에서 받는다. 합집합 계산 금지 | 2-2 A, C-07 |

### 6-2. 표준형 4종 — 개별 문구가 없으면 이것을 쓴다

| 유형 | 표준 문구 | 표시 위치 |
|---|---|---|
| 권한 없음 | "이 페이지에 들어올 권한이 없어요." | 전체 화면 + [홈으로] |
| 찾을 수 없음 | "찾는 내용이 없어요. 삭제됐을 수 있어요." | 전체 화면 + [뒤로] |
| 서버 오류 | "잠시 문제가 생겼어요. 조금 뒤에 다시 시도해 주세요." | 전체 화면 또는 토스트 + [다시 시도] |
| 입력 검증 | "{항목}을 입력해 주세요." / "{항목}은 {N}자까지 쓸 수 있어요." | 입력창 바로 아래 인라인 + 빨간 테두리 |

**표시 위치 4원칙** — ① 입력 검증 = 인라인 ② 가벼운 성공·실패 = 토스트 3초 ③ **되돌릴 수 없는 행동 = 확인 다이얼로그** ④ 화면 전체가 불가능 = 전체 화면 대체.

> 조사 처리: "{항목}을/를" "{항목}은/는"은 받침에 따라 바꾼다 **(제안)**. 목업 W-13에서 "배운 점을(를)"을 "배운 점을"로 고친 이력이 있다 (인계 2026-09-29).

## 8. 서버 오류 코드 계약 (제안)

Spring for GraphQL은 HTTP 200 안에 `errors[].extensions`로 오류를 준다. 프론트가 **오류 메시지 원문을 화면에 쓰지 않고**(5-2-8 용어 규칙) 정해진 문구를 고르려면 코드가 필요하다. 목 API는 아래 코드를 그대로 낸다.

| 코드 (제안) | 분류 | 예외 | 화면 | 프론트 반응 |

## 11. 의뢰인 확인 필요

팀이 정할 수 있는 것(문구 다듬기, 라벨 통일, 컴포넌트 방식)은 넣지 않았다. 아래는 **판정 규칙이나 확정 문서의 문언을 바꾸는 것**만이다.

| # | 질문 | 왜 필요한가 | 걸리는 곳 |
|---|---|---|---|
| Q-A1 | **오늘 쓴 기록글은 인증일 수에 바로 반영되나요, 다음 날 오전 6시 갱신 뒤에 반영되나요?** | 5-2-6은 "인증일 수 = 하루 1번 새벽 일괄", "기록글 수 = 실시간"이라 적었다. 문언대로면 글을 쓰면 기록글은 1/1 ✓이 되는데 인증일은 다음 날까지 그대로라 회원이 혼란스럽다. 잔디만 6시 기준이고 기록글로 생긴 인증일은 실시간이라면 "오늘 오전 6시 기준" 표기의 대상도 바뀐다 | CM-01 ②③, TM-05, AC-01 ②④, 5-2-6 |
